\section{Experiment Design}
\label{sec:experimentdesign}

All experiments were conducted on a dedicated Linux server used exclusively for
inference workloads during the experimental campaign. The server hardware and
software environment are summarised in Table~\ref{tab:server}. The GPU is the
primary compute resource: all LLM inference is offloaded to it via Ollama, which
manages model loading, quantisation, and batching transparently.

\begin{table}[H]
\centering
\arrayrulecolor{black}
\begin{tabular}{|l|l|}
\hline
\rowcolor{bluePoli!30}
\textbf{Component} & \textbf{Specification} \T\B \\
\hline
Server model     & Dell PowerEdge R760 \T\B \\
\hline
GPU model        & NVIDIA L40S \T\B \\
\hline
GPU VRAM         & 45 GiB \T\B \\
\hline
CPU model        & Intel Xeon Gold 6426Y (×2) \T\B \\
\hline
CPU cores / threads & 32 / 64 \T\B \\
\hline

\end{tabular}
\caption{Server hardware and software specifications.}
\label{tab:server}
\end{table}

Ollama runs as a persistent background service on the host machine, exposing a
local REST endpoint at \texttt{localhost:11434}. All three models evaluated in
the thesis --- \texttt{gemma4:e4b}, \texttt{gemma4:26b}, and
\texttt{mistral-small3.2:24b} --- were downloaded from the Ollama model library
and served locally, with no external network access during inference. An OpenAI
API key is required only for the ground-truth judge, which calls
\texttt{gpt-5.4} to score both the natural-language analysis step and the
visualization step.

The agent itself runs inside a Docker container built from the repository
Dockerfile. The image is based on \texttt{python:3.12-slim} and installs all
Python dependencies from \texttt{requirements.txt}. Two environment variables
are set at build time: \texttt{MPLBACKEND=Agg} to enable headless chart
rendering, and \texttt{OLLAMA\_HOST=http://localhost:11434} as the default
Ollama endpoint. The host \texttt{runs/} directory is mounted as a volume to
persist experiment results across container restarts. The
\texttt{--network=host} flag allows the container to reach the Ollama service
running on the host. The image is built once from the repository root:

\begin{verbatim}
docker build -t data-agent .
\end{verbatim}

Tests 01 through 04 are executed via this same container and are fully
orchestrated by the helper script
\texttt{evaluation/\allowbreak run\_thesis\_final\_tests\_01\_04\_docker.sh},
which loops over all model and repeat combinations sequentially. Test 05,
whose configurations depend on the findings of the preceding tests, is run
with individual \texttt{docker run} invocations as described in
Section~\ref{subsec:test05}.

Before executing the tests in the definitive form described below, a lighter
version of the same experiments was first run --- with fewer repetitions and a
smaller number of sampled parameter configurations --- to explore preliminary
results and guide the design of the full test suite. For clarity and
conciseness, these preliminary runs are not reported here, as they constitute
a reduced variant of the tests described in the following subsections.

\subsection{Test 01 - Baseline Model Comparison}
\label{subsec:test01}

Test 01 establishes the quality and energy baseline for the three candidate
models evaluated in this thesis: \texttt{gemma4:e4b}, \texttt{gemma4:26b}, and
\texttt{mistral-small3.2:24b}. Each model runs with a fixed default
configuration so that any observed differences in output quality, latency, and
energy consumption are attributable solely to the model itself rather than to
configuration choices. Rather than choosing these defaults arbitrarily, the
baseline parameters for each model are taken directly from the recommended
settings published on the respective Ollama model pages. The resulting
per-model configurations are summarised in Table~\ref{tab:test01baseline}.

The evaluation is performed on the full 20-prompt benchmark, stratified across
four SQL difficulty levels. For each prompt, three complementary quality scores
are recorded: the row-level Intersection-over-Union (\texttt{csv\_iou}) for
data retrieval accuracy, the LLM-as-judge score (\texttt{text\_score}) for the
natural-language analysis, and the LLM-as-judge score (\texttt{vis\_score}) for
visualization correctness when a chart is expected. In addition, per-step
execution time and energy consumption are tracked via CodeCarbon. Each model
configuration is repeated three times to allow variance estimation.

The results of this test inform the selection of the reference baseline for all
subsequent tests and provide the first evidence of whether model size, the
presence of an internal chain-of-thought reasoning mechanism, and the
mixture-of-experts architecture lead to meaningful accuracy or efficiency
differences on this agentic workload.

\subsection{Test 02 - Per-Agent Sensitivity Analysis (OFAT)}
\label{subsec:test02}

Test 02 adopts a One-Factor-At-a-Time (OFAT) protocol to quantify how
individual static sampling hyperparameters affect each agent step in isolation.
In each phase, only one agent step's parameters are varied while the other two
steps are kept at the model's baseline configuration. The three phases target,
in order, the \texttt{lookup\_sales\_data} step (primary metric:
\texttt{csv\_iou}), the \texttt{analyzing\_data} step (primary metric:
\texttt{text\_score}), and the \texttt{create\_visualization} step (primary
metric: \texttt{vis\_score}). In addition to the step-specific metric, the
full-pipeline \texttt{quality\_mean} is also tracked so that improvements or
regressions in the varied step can be related to the overall agent output.

The experiment varies five static sampling parameters, one at a time, each
across ten deterministic values centred around the model-specific baseline:

\begin{itemize}
    \item \textbf{temperature} — 10 values covering the range below and above
          the baseline (model-specific: Gemma~4 range $[0.50,\,1.30]$, centred
          at 1.0; Mistral~Small range $[0.03,\,0.45]$, centred at 0.15);
    \item \textbf{top-$p$} — 10 values in $[0.70,\,1.00]$, same for all models;
    \item \textbf{top-$k$} — 10 values in $\{16, 20, 24, 32, 40, 48, 56, 80,
          96, 128\}$, same for all models;
    \item \textbf{repeat\_penalty} — 10 values in $[0.90,\,1.30]$, same for
          all models;
    \item \textbf{repeat\_last\_n} — 10 values in $\{16, 24, 32, 40, 48, 56,
          80, 96, 128, 256\}$, same for all models.
\end{itemize}

No Best-of-$N$ or Chain-of-Thought strategies are included in this test: $n=1$
and \texttt{cot\_n}$=1$ are fixed throughout, so all configurations differ only
in their static sampling settings. The grid is fully deterministic: for each
step, one baseline configuration plus $5 \times 10 = 50$ off-baseline
configurations are generated, yielding \textbf{51 configurations per step} and
$51 \times 3 = 153$ total configurations per model. The experiment is run on a
15-prompt benchmark subset to reduce wall-clock time while retaining enough
prompt diversity for reliable per-step sensitivity estimates, for three
independent repeats per model, yielding $153 \times 15 = 2{,}295$ scored prompt
runs per model per repeat.

The main goal of this test is to identify which static parameters and which
agent steps offer the most leverage for quality improvement at low computational
cost, before considering more expensive compute-expansion strategies in Test 04.

\subsection{Test 03 - \texttt{max\_tokens} Ladder per Agent}
\label{subsec:test03}

Test 03 isolates the effect of the token budget on each agent step by sweeping
four \texttt{max\_tokens} values for one step at a time, keeping the other two
steps at generous caps that are unlikely to be binding. The token levels tested
for each step are:

\begin{itemize}
    \item \texttt{lookup\_sales\_data}: 2500, 3000, 5000 (baseline), 8000
    \item \texttt{analyzing\_data}: 4000, 5000, 7000 (baseline), 10000
    \item \texttt{create\_visualization}: 4000, 5000, 7000 (baseline), 10000
\end{itemize}

The rationale is that \texttt{max\_tokens} is an upper bound on the number of
tokens the model can generate in a single call, not a fixed generation length.
A too-low cap can cause structural failures --- truncated SQL queries, incomplete
analysis text, or missing chart code --- while a cap that is already non-binding
adds no measurable cost. The experiment therefore aims to identify the minimum
safe cap for each step and model, and to verify whether higher caps provide any
quality benefit beyond that threshold.

The test runs on a 10-prompt benchmark subset across all three models, for three
repeats each, yielding $12 \times 10 = 120$ scored prompt runs per model per
repeat. Both step-specific metrics and the full-pipeline \texttt{quality\_mean}
are reported alongside per-step energy measurements, so that any accuracy
recovery from a higher cap can be weighed against its compute cost.

\subsection{Test 04 - Compute Expansion (CoT Depth Ladder)}
\label{subsec:test04}

Test 04 investigates whether Chain-of-Thought (CoT) refinement can improve
accuracy over the static baselines established in Tests 02--03.
\texttt{gemma4:26b} is excluded: its main weakness (visualization) was already
resolved by the token-budget increase in Test 03, its SQL and text steps were
near saturation, and its high baseline latency made compute expansion
particularly costly.

Both \texttt{gemma4:e4b} and \texttt{mistral-small3.2:24b} are evaluated with
the same protocol: a CoT depth ladder varying \texttt{cot\_n} $\in \{1, 2, 3,
4\}$ on the lookup and visualization steps independently, while the analysis
step is kept fixed at baseline. This yields 8 configurations per model (4
lookup $\times$ 2 steps), run on the same 10-prompt subset as Test 03 for
three repeats.

An additional follow-up campaign (Test 04b) is run on \texttt{gemma4:e4b} to
disentangle whether lookup gains come from CoT refinement or from the
temperature value of the first generation pass. It compares three static
temperature settings ($t \in \{0.3, 0.6, 0.8\}$) against three Best-of-2
temperature ranges (narrow, medium, wide) and a CoT $n=2$ reference, across
8 lookup-only configurations and two repeats.

\subsection{Test 05 - Final Pareto Confirmation}
\label{subsec:test05}

Test 05 is the final evaluation stage. Its purpose is to confirm whether the
best configurations identified in Tests 02--04 maintain their advantage on the
full 20-prompt benchmark, and to establish the definitive quality-versus-energy
Pareto frontier across all models and candidate policies.

Unlike the preceding tests, which vary one hyperparameter dimension at a time,
Test 05 evaluates complete agent policies: each configuration specifies the
full set of per-step parameters assembled from the most promising candidates of
the exploratory phase. Six configurations are evaluated per model. Five are
common to all three models:

\begin{itemize}
    \item \textbf{baseline} --- the fixed default from Test 01, used as
          the reference point for measuring tuning gains;
    \item \textbf{efficient\_static} --- the best static-parameter policy
          that improves quality with minimal energy overhead;
    \item \textbf{best\_step\_static} --- the per-step best static settings
          from the OFAT and token-ladder experiments, combined;
    \item \textbf{max\_tokens\_adjusted} --- a token-cap-only variant to
          isolate the contribution of the token budget;
    \item \textbf{combined\_best\_candidate} --- a combination of the
          top-performing settings across all steps, as a stress test of
          whether exploratory gains are additive.
\end{itemize}

The sixth configuration is model-specific and targets each model's most
promising compute-expansion or efficiency candidate:

\begin{itemize}
    \item \texttt{gemma4:e4b} --- \textbf{lookup\_cot\_n2}: SQL repair via
          Chain-of-Thought on the lookup step;
    \item \texttt{gemma4:26b} --- \textbf{visualization\_bon\_top\_k\_n2}:
          Best-of-2 with top-$k$ sampling on the visualization step;
    \item \texttt{mistral-small3.2:24b} --- \textbf{analysis\_top\_k\_high\_low\_tokens}:
          analysis top-$k$ tuning combined with reduced token caps across
          all steps.
\end{itemize}

All three models are evaluated on the full 20-prompt benchmark for three
repeats, yielding $6 \times 20 = 120$ scored prompt runs per model per repeat.
The primary metrics are \texttt{quality\_mean}, prompt-level end-to-end quality
(which penalises missing downstream scores caused by upstream failures),
completion rate, elapsed time, and energy per prompt.
