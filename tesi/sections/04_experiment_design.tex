\section{Experiment Design}
\label{sec:experimentdesign}

The experimental campaign is structured into five experiments, each isolating a distinct
aspect of model behaviour or configuration:

\begin{itemize}
    \item \textbf{Test 01 --- Baseline Model Comparison}: runs each candidate
          model with its Ollama-recommended default configuration on the full
          20-prompt benchmark to establish a quality and efficiency reference.
    \item \textbf{Test 02 --- Per-Agent Sensitivity Analysis}: sweeps five
          static sampling hyperparameters one at a time (One-Factor-At-a-Time,
          OFAT) across each agent step to quantify their individual effect on
          pipeline quality.
    \item \textbf{Test 03 --- \texttt{max\_tokens} Ladder per Agent}: varies
          the output token budget for each agent step across four discrete
          levels to identify the minimum safe cap and any quality sensitivity
          to the budget.
    \item \textbf{Test 04 --- Compute Expansion (CoT Depth Ladder)}: applies
          Chain-of-Thought refinement at depths 1--4 on the lookup and
          visualization steps; a targeted follow-up (Test~04b) checks whether
          Best-of-N temperature sampling provides genuine lookup benefit
          through candidate selection.
    \item \textbf{Test 05 --- Final Pareto Confirmation}: evaluates the most
          promising combined configurations from Tests~02--04 on the full
          benchmark to establish the definitive quality-versus-energy Pareto frontier.
\end{itemize}

The campaign was carried out across two hardware environments.
Tests 01, 02, and 05 were conducted on a dedicated remote Linux server used
exclusively for inference workloads; its hardware and software specifications
are reported in Table~\ref{tab:server}. Tests 03, 04, and 04b were instead
executed on a separate Linux server whose specifications are reported in
Table~\ref{tab:server_local}; this split was adopted to run the two groups
of experiments in parallel and shorten the overall data-collection time.
In both environments the GPU is the primary compute resource: all LLM
inference is offloaded to it via Ollama.
The difference in hardware does not affect the validity of the conclusions
drawn from Tests 03, 04, and 04b, because those tests measure only
\emph{relative} effects: each sweep varies a single parameter across a
fixed set of configurations that are all executed on the same machine,
under identical software and model conditions. Absolute latency and energy
figures are therefore not directly comparable across the two servers, but
the rankings, sensitivity trends, and relative improvements that those
tests are designed to capture remain unaffected by the hardware on which
they are run.

Ollama runs as a persistent background service on the host machine, exposing a
local REST endpoint at \texttt{localhost:11434}. All three models evaluated in
the thesis --- \texttt{gemma4:e4b}, \texttt{gemma4:26b}, and
\texttt{mistral-small3.2:24b} --- were downloaded from the Ollama model library
and served locally, with no external network access during inference. An OpenAI
API key is required only for the ground-truth judge, which calls
\texttt{gpt-5.4} to score both the natural-language analysis step and the
visualization step.

All benchmark runs are launched from deterministic YAML manifests and write
their outputs to a persistent \texttt{runs/} directory. For clean energy
attribution, model/configuration/repeat combinations are executed in series:
only one benchmark process runs on the measured GPU at a time. This means that
each CodeCarbon measurement corresponds to a single atomic agent run rather
than to a concurrent workload sharing the same accelerator. The orchestration
scripts are used only to automate this ordered sequence and to resume incomplete
runs; they do not parallelise configurations whose energy values are later
compared.

Before executing the tests in the definitive form described below, a lighter
version of the same experiments was first run --- with fewer repetitions and a
smaller number of sampled parameter configurations --- to explore preliminary
results and guide the design of the full test suite. For clarity and
conciseness, these preliminary runs are not reported here, as they constitute
a reduced variant of the tests described in the following subsections.

\subsection{Test 01 - Baseline Model Comparison}
\label{subsec:test01}

Test 01 establishes the quality and energy baseline for the three candidate
models evaluated in this thesis: \texttt{gemma4:e4b}, \texttt{gemma4:26b}, and
\texttt{mistral-small3.2:24b}. Each model runs with a fixed default
configuration so that any observed differences in output quality, latency, and
energy consumption are attributable solely to the model itself rather than to
configuration choices. Rather than choosing these defaults arbitrarily, the
baseline parameters for each model are taken directly from the recommended
settings published on the respective Ollama model pages. The resulting
per-model configurations are summarised in Table~\ref{tab:test01baseline}.

The evaluation is performed on the full 20-prompt benchmark, stratified across
four SQL difficulty levels. For each prompt, three complementary quality scores
are recorded: the graded ground-truth table-similarity score
(\texttt{csv\_iou}) for data retrieval accuracy, the LLM-as-judge score
(\texttt{text\_score}) for the
natural-language analysis, and the LLM-as-judge score (\texttt{vis\_score}) for
visualization correctness when a chart is expected. In addition, per-step
execution time and energy consumption are tracked via CodeCarbon. Each model
configuration is repeated three times to allow variance estimation.

The results of this test inform the selection of the reference baseline for all
subsequent tests and provide the first evidence of whether model size, the
presence of an internal chain-of-thought reasoning mechanism, and the
mixture-of-experts architecture lead to meaningful accuracy or efficiency
differences on this agentic workload.

\subsection{Test 02 - Per-Agent Sensitivity Analysis (OFAT)}
\label{subsec:test02}

Test 02 adopts a One-Factor-At-a-Time (OFAT) protocol to quantify how
individual static sampling hyperparameters affect each agent step in isolation.
In each phase, only one agent step's parameters are varied while the other two
steps are kept at the model's baseline configuration. The three phases target,
in order, the \texttt{lookup\_sales\_data} step (primary metric:
\texttt{csv\_iou}), the \texttt{analyzing\_data} step (primary metric:
\texttt{text\_score}), and the \texttt{create\_visualization} step (primary
metric: \texttt{vis\_score}). In addition to the step-specific metric, the
full-pipeline \texttt{quality\_mean} is also tracked so that improvements or
regressions in the varied step can be related to the overall agent output.

The experiment varies five static sampling parameters, one at a time, each
across ten deterministic values centred around the model-specific baseline:

\begin{itemize}
    \item \textbf{temperature} — 10 values covering the range below and above
          the baseline (model-specific: Gemma~4 range $[0.50,\,1.30]$, centred
          at 1.0; Mistral~Small range $[0.03,\,0.45]$, centred at 0.15);
    \item \textbf{top-$p$} — 10 values in $[0.70,\,1.00]$, same for all models;
    \item \textbf{top-$k$} — 10 values in $\{16, 20, 24, 32, 40, 48, 56, 80,
          96, 128\}$, same for all models;
    \item \textbf{repeat\_penalty} — 10 values in $[0.90,\,1.30]$, same for
          all models;
    \item \textbf{repeat\_last\_n} — 10 values in $\{16, 24, 32, 40, 48, 56,
          80, 96, 128, 256\}$, same for all models.
\end{itemize}

No Best-of-$N$ or Chain-of-Thought strategies are included in this test: $n=1$
and \texttt{cot\_n}$=1$ are fixed throughout, so all configurations differ only
in their static sampling settings. The grid is fully deterministic: for each
step, one baseline configuration plus $5 \times 10 = 50$ off-baseline
configurations are generated, yielding \textbf{51 configurations per step} and
$51 \times 3 = 153$ total configurations per model. The experiment is run on a
15-prompt benchmark subset to reduce wall-clock time while retaining enough
prompt diversity for reliable per-step sensitivity estimates, for two
independent repeats per model, yielding $153 \times 15 = 2{,}295$ scored prompt
runs per model per repeat.

The main goal of this test is to identify which static parameters and which
agent steps offer the most leverage for quality improvement at low computational
cost, before considering more expensive compute-expansion strategies in Test 04.

\subsection{Test 03 - \texttt{max\_tokens} Ladder per Agent}
\label{subsec:test03}

Test 03 isolates the effect of the token budget on each agent step by sweeping
four \texttt{max\_tokens} values for one step at a time, keeping the other two
steps at generous caps that are unlikely to be binding. The token levels tested
for each step are:

\begin{itemize}
    \item \texttt{lookup\_sales\_data}: 2500, 3000, 5000 (baseline), 8000
    \item \texttt{analyzing\_data}: 4000, 5000, 7000 (baseline), 10000
    \item \texttt{create\_visualization}: 4000, 5000, 7000 (baseline), 10000
\end{itemize}

The rationale is that \texttt{max\_tokens} is an upper bound on the number of
tokens the model can generate in a single call, not a fixed generation length.
A too-low cap can cause structural failures --- truncated SQL queries, incomplete
analysis text, or missing chart code --- while a cap that is already non-binding
should add little measurable cost. The experiment therefore aims to identify the
minimum safe cap for each step and model, to verify whether higher caps provide
any quality benefit beyond that threshold, and to check empirically whether
larger caps introduce a significant energy increase.

The test runs on a 10-prompt benchmark subset across all three models, for three
repeats each, yielding $12 \times 10 = 120$ scored prompt runs per model per
repeat. The subset is reduced from the 15~prompts used in Test~02 to limit
total wall-clock time, while preserving coverage of all four SQL difficulty
levels (D1:~2, D2:~3, D3:~3, D4:~2 prompts). Both step-specific metrics and the full-pipeline \texttt{quality\_mean}
are reported alongside per-step energy measurements, so that any accuracy
recovery from a higher cap can be weighed against its compute cost.

\subsection{Test 04 - Compute Expansion (CoT Depth Ladder)}
\label{subsec:test04}

Test 04 investigates whether Chain-of-Thought (CoT) refinement can improve
accuracy over the static baselines established in Tests 02--03.
\texttt{gemma4:26b} is excluded: its main weakness (visualization) was already
resolved by the token-budget increase in Test 03, its SQL and text steps were
near saturation, and its high baseline latency made compute expansion
particularly costly.

Both \texttt{gemma4:e4b} and \texttt{mistral-small3.2:24b} are evaluated with
the same protocol: a CoT depth ladder varying \texttt{cot\_n} $\in \{1, 2, 3,
4\}$ on the lookup and visualization steps independently, while the analysis
step is kept fixed at baseline. This yields 8 configurations per model (4
lookup $\times$ 2 steps), run on the same 10-prompt subset as Test~03 for
three repeats, for the same reason of limiting total run time while
retaining full difficulty coverage.

An additional follow-up campaign (Test 04b) is run on \texttt{gemma4:e4b} to
disentangle whether lookup gains come from CoT refinement, from a better static
temperature, or from genuine Best-of-N candidate selection. It compares three
static temperature settings ($t \in \{0.3, 0.6, 0.8\}$) against three
Best-of-3 temperature ranges --- narrow $[0.8,1.0]$, medium $[0.6,1.0]$, and
wide $[0.3,1.0]$ --- plus a CoT $n=2$ reference, across 8 lookup-only
configurations and three repeats. The use of $n=3$ is deliberate: with only
two candidates the no-GT selector has too little ranking signal to test whether
Best-of-N is actually choosing among alternatives.

\subsection{Test 05 - Final Pareto Confirmation}
\label{subsec:test05}

Test 05 is the final evaluation stage. Its purpose is to confirm whether the
best configurations identified in Tests 02--04 maintain their advantage on the
full 20-prompt benchmark, and to establish the definitive quality-versus-energy
Pareto frontier across all models and candidate policies.

Unlike the preceding tests, which vary one hyperparameter dimension at a time,
Test 05 evaluates combined agent policies: each configuration specifies the
full set of per-step parameters assembled from the most promising candidates of
the exploratory phase. A substantial part of the test consists of newly run
combined policies designed specifically for this final confirmation stage,
rather than only reusing rows from earlier experiments. Eight to ten
configurations are evaluated per model, each combining one or more of the
interventions from Tests 02--04: lookup Chain-of-Thought (varying
\texttt{cot\_n} from 2 to~4), static lookup temperature tuning
(\texttt{temp}~0.8), and reduced downstream token caps.

The configuration families are model-specific:

\begin{itemize}
    \item \texttt{gemma4:e4b} --- combinations of lookup CoT
          (\texttt{cot\_n}~2 or~4), low-temperature lookup
          (\texttt{temp}~0.8), and reduced token caps across downstream
          steps;
    \item \texttt{gemma4:26b} --- visualization top-$k$ sampling
          (\texttt{top\_k}~20), lookup CoT (\texttt{cot\_n}~2 or~3),
          combined static parameter sets, and reduced token caps;
    \item \texttt{mistral-small3.2:24b} --- lookup CoT (\texttt{cot\_n}~2
          or~3) with efficient token budgets, and combined static parameter
          sets with varied token caps.
\end{itemize}

The final candidate set combines the Test~01 baselines, the newly measured
combined Test~05 policies, and useful configurations that had already been
measured in Tests~02--04. This reuse is intentional: the purpose of Test~05 is
to compare the best available candidate policies, not to rerun every
configuration whose result was already known under the same judging setup.

The primary metrics are \texttt{quality\_mean}, prompt-level end-to-end
quality (which penalises missing downstream scores caused by upstream
failures), completion rate, elapsed time, and energy per prompt.

\paragraph{Energy as the efficiency axis.}
Although execution time and energy are both recorded, they are treated as
two readings of the same underlying cost rather than as independent axes.
On fixed inference hardware the accelerator draws a near-constant average
power during generation, so per-prompt energy is, to first order, a fixed
multiple of wall-clock latency; the baseline campaign confirms this, with
the per-model latency and energy rankings coinciding to within about five
percentage points. \textit{The quality--cost trade-offs and Pareto frontiers in
Section~\ref{sec:experiments} therefore use energy per prompt as the single
representative efficiency axis}, while absolute latency is still reported in
the per-test tables for deployments bound by response-time limits. Energy
is preferred as the headline axis because it simultaneously captures the
sustainability dimension and, unlike wall-clock time, aggregates the CPU,
GPU, and RAM contributions measured by CodeCarbon.
