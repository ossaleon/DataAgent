\section{Experimental Results}
\label{sec:experiments}

\subsection{Test 01 - Baseline Model Comparison}
\label{subsec:res01}

Test~01 establishes the quality and efficiency baseline for the three
candidate models before any parameter tuning is applied. The experimental
design is described in Section~\ref{subsec:test01}: each model runs with its
Ollama-recommended sampling defaults over all 20 benchmark prompts, with no
agent step varied. One complete run per model was collected as a first-pass
baseline; the planned additional repeats would allow variance estimation
but do not alter the qualitative findings reported here.

\subsubsection{Quality Metrics and End-to-End Interpretation}

The benchmark runner reports a standard \texttt{quality\_mean} defined as the
arithmetic mean of the three component score means:
\begin{equation}
\texttt{quality\_mean} = \frac{1}{3}\bigl(\overline{\texttt{csv\_iou}} +
                                           \overline{\texttt{text\_score}} +
                                           \overline{\texttt{vis\_score}}\bigr)
\label{eq:quality_mean}
\end{equation}
where the averages are taken over the subset of prompts that produced a
scorable output for each component. This definition is consistent across
all tests and is used for continuity, but it can mask pipeline failures:
when the lookup step returns an empty or erroneous SQL result, the text
and visualization agents are never reached, so the resulting missing
scores are simply excluded from the denominators of the text and
visualization means, leaving the official \texttt{quality\_mean}
artificially high.

To address this, two additional quality views are used throughout this test:

\begin{itemize}
    \item \textbf{Component E2E quality} — the same three-component mean,
          but any expected score absent due to an upstream pipeline failure
          is counted as~$0.0$ rather than excluded. This is the primary
          accuracy metric for comparisons in this section.
    \item \textbf{Prompt E2E quality} — the per-prompt mean of the expected
          component scores, with missing expected outputs counted as~$0.0$.
          This view penalises each failed prompt as a single unit,
          regardless of how many components were expected from it.
\end{itemize}

\subsubsection{Per-Model Error Analysis}
\label{subsubsec:test01errors}

\paragraph{\texttt{gemma4:e4b}.}
The two hard failures occur on prompts~4 and~17, both requiring a comparison
of average monthly revenue across different store segmentation dimensions over
2022 and~2023. The generated SQL queries attempt the correct nested monthly
aggregation logic but reference incorrect column aliases or date fields in the
outer subquery, causing the lookup step to return empty results
(\texttt{csv\_iou}~$= 0.0$). No text or visualization output is produced for
either prompt as a result.

A third partial failure occurs on prompt~14 (top brands by average
selling price): the CSV similarity remains high (\texttt{csv\_iou}~$= 0.973$)
but the analysis agent transposes the average selling price and total unit
count values in its narrative, yielding \texttt{text\_score}~$= 0.5$.
Both failure types suggest that this model requires lookup-step targeted
improvements for complex temporal aggregations, motivating the Best-of-$N$
and Chain-of-Thought strategies evaluated in Test~04.

\paragraph{\texttt{gemma4:26b}.}
The model completes all SQL and text steps without failure. Its main
weakness is concentrated in the visualization agent:

\begin{itemize}
    \item \textbf{Prompt~10} (monthly revenue for a specific product class
          as a line chart): perfect data retrieval (\texttt{csv\_iou}~$= 1.0$)
          and a high text score, but \texttt{vis\_score}~$= 0.0$ because no
          chart code was produced at all.
    \item \textbf{Prompt~16} (grouped bar chart for organic vs.\ non-organic
          revenue by region): near-perfect SQL (\texttt{csv\_iou}~$= 0.974$)
          and good text (\texttt{text\_score}~$= 0.875$), but weak
          visualization (\texttt{vis\_score}~$= 0.592$) because the organic
          flag was treated as a numerical $y$-axis value rather than a grouping
          variable.
\end{itemize}

These failures suggest that the larger Gemma model's visualization step is
the primary target for parameter tuning, as explored in Tests~02 and~03.

\paragraph{\texttt{mistral-small3.2:24b}.}
The model completes all prompts without SQL errors. Its main weakness is
analytical completeness: on prompts~7, 8, and~16, the CSV output is correct
or near-correct but the natural-language analysis omits relevant comparisons,
leading to partial text scores. Prompt~18 (promo revenue share by product
category) illustrates a schema adherence issue: the model returns a
semantically correct table but with extra columns and a percentage-formatted
column name that does not match the expected compact schema
(\texttt{csv\_iou}~$= 0.546$, \texttt{vis\_score}~$= 0.664$, despite a
high text score of~0.875). Analysis wording completeness and strict output
schema adherence are the likely tuning targets for this model.

\subsubsection{Summary}

The main findings of Test~01 can be summarised as follows:

\begin{enumerate}
    \item \textbf{Mistral Small dominates at baseline.}
          \texttt{mistral-small3.2:24b} achieves the best component E2E
          quality (0.9265), the lowest latency (112.5~s/prompt), and the
          lowest energy consumption (0.00705~kWh/prompt). It serves as the
          primary efficiency reference for all subsequent tests.

    \item \textbf{Gemma~26B improves SQL and text reliability at high cost.}
          \texttt{gemma4:26b} achieves near-perfect SQL accuracy
          (\texttt{csv\_iou}~$= 0.999$) and the highest text score (0.944),
          but requires 2.0$\times$ the time and 1.6$\times$ the energy of
          Mistral for only a 2.4\,\% gain in prompt E2E quality. Its
          visualization step is unexpectedly both weak and expensive.

    \item \textbf{Gemma~E4B is brittle on hard SQL.}
          The small thinking model is competitive at difficulties~1 through~3
          but collapses at difficulty~4, where two nested monthly aggregation
          queries trigger complete SQL failures. This motivates the
          lookup-step targeted interventions in Tests~02 and~04.

    \item \textbf{Visualization is the dominant energy lever.}
          The visualization step accounts for 51--64\,\% of per-prompt LLM
          energy across all models and is the agent step with the greatest
          potential for efficiency improvement through parameter tuning.
\end{enumerate}

\subsection{Test 02 - Per-Agent Sensitivity Analysis (OFAT)}
\label{subsec:res02}

Test~02 applies a One-Factor-At-a-Time (OFAT) protocol to quantify how
individual static sampling hyperparameters affect each agent step in
isolation. The experimental design is described in
Section~\ref{subsec:test02}: each of the five parameters
(\texttt{temperature}, \texttt{top\_p}, \texttt{top\_k},
\texttt{repeat\_penalty}, \texttt{repeat\_last\_n}) is swept
individually across ten values per step, producing 153 configurations
per model. Each configuration is repeated twice over a 15-prompt subset
of the benchmark, reduced from the full 20-prompt set to limit total
run time while preserving the original difficulty distribution across
all four SQL complexity levels (difficulty~1: 3~prompts, difficulty~2:
4~prompts, difficulty~3: 5~prompts, difficulty~4: 3~prompts).

\subsubsection{Per-Model Analysis}

\paragraph{\texttt{gemma4:26b}.}

The sensitivity profile of \texttt{gemma4:26b} is strongly step-specific
and consistently asymmetric. The visualization step is unambiguously the
highest-leverage target: every parameter family improves it, and the
gains are large enough (up to $+6.8\%$ quality, $+5.2\%$
\texttt{vis\_score}) to be practically meaningful and to more than
offset the inter-repeat noise floor characterised in
Section~\ref{subsubsec:test02stability}. The lookup step shows
meaningful positive potential ($+3.2\%$ quality via
\texttt{repeat\_last\_n\_96}) but also a very steep downside risk: a
single bad \texttt{top\_k} value can collapse quality by~$-12.3\%$,
likely by disrupting the structured SQL generation. The analysis step is
the most fragile: temperature changes in particular push the model into
degenerate outputs, and the safe operating window for this step is
narrow around the baseline.

\paragraph{\texttt{mistral-small3.2:24b}.}

\texttt{mistral-small3.2:24b} is almost entirely insensitive to the
parameters tested. The best achievable quality delta at any step is
$+0.007$, which is within the inter-repeat noise range. The model's
low baseline temperature (0.15) and the non-thinking architecture
appear to make its output distribution far less responsive to sampling
parameter perturbations than the thinking model. The practical
implication is that static parameter tuning offers negligible quality
improvement for Mistral, and that pursuing efficiency gains for this
model requires structural changes rather than hyperparameter search.
The sole exception is the \texttt{analysis\_repeat\_penalty\_1.2}
misconfiguration described above, which serves as a warning against
assuming that insensitivity to improvement implies insensitivity to
regression.

The model appears to generate complete, well-formed outputs even at
moderate token caps, so additional headroom does not translate into
measurable quality gains.
This is a practically useful property: the cap can be set conservatively
to limit resource use without risking quality regression.

\subsection{Test 04 - Compute Expansion via Chain-of-Thought}
\label{subsec:res04}

Test~04 evaluates Chain-of-Thought (CoT) iterations as a compute
expansion strategy for the lookup and visualization steps. Each
configuration requests \texttt{cot\_n}~$\in \{1, 2, 3, 4\}$ refinement
iterations, where \texttt{cot\_n}~$= 1$ is the single-call baseline. An
early-stop mechanism halts the loop when the model signals that the
previous output is already satisfactory, so the executed depth can be
lower than the requested depth. The test was run on

\texttt{gemma4:26b} was excluded because its baseline quality is already
the highest of the three models, making CoT a less compelling lever:
the headroom for improvement is smaller and the per-prompt cost is
already the highest, so additional compute iterations carry a less
favourable return than for the two lighter models.

The Gemma~E4B lookup curve deserves particular attention: the gain from

tends to over-edit working code, introducing regressions rather than
