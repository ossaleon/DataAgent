# Test 04: Gemma E4B Compute Expansion

## Objective

Measure whether extra inference calls improve Gemma E4B accuracy enough to justify their time and energy cost. This test is step-isolated like Test 03: only one agent step changes at a time, while the other two stay fixed at the Gemma E4B baseline.

## Model

```text
gemma4:e4b
```

Reason: this test is a focused follow-up on the small thinking model. It should answer whether a cheap thinking model can recover accuracy through controlled extra computation.

## Hypothesis

Best-of-N and CoT increase compute by design. They are useful only if the selected or refined output improves the varied step beyond baseline noise.

Expected behavior:

```text
lookup_sales_data      may benefit from candidate diversity and SQL correction
analyzing_data         may benefit from candidate diversity, but not from CoT in this test
create_visualization   may benefit from controlled diversity and feedback correction
```

Do not combine `n > 1` and `cot_n > 1` in the same config. That would make the compute increase hard to attribute.

## Baseline Defaults

All fixed steps use Gemma E4B baseline settings:

```text
temperature=1.0
top_p=0.95
top_k=64
n=1
cot_n=1
max_tokens lookup_sales_data=5000
max_tokens analyzing_data=7000
max_tokens create_visualization=7000
```

Best-of-N candidates are generated by varying the selected `bon_param` linearly across its configured min and max. All non-selected sampling parameters stay fixed.

## Pilot Evidence Used For This Design

The previous Gemma E4B screening run showed three useful signals:

```text
lookup temperature changes were highly sensitive:
  temperature_low  delta_quality=-0.144
  temperature_high delta_quality=-0.188

analysis top_k_low improved quality:
  top_k_low delta_quality=+0.038

visualization top_k_low and CoT were the strongest positive signals:
  top_k_low delta_quality=+0.075
  cot_n2    delta_quality=+0.079
```

The earlier Best-of-N configs mostly increased `n` while leaving the candidate range at baseline values. This test makes the varied Best-of-N parameter explicit, so it tests real candidate diversity instead of repeated baseline sampling.

## Best-of-N Parameter Choices

Lookup uses:

```text
bon_param=temperature
```

Reason: SQL generation is sensitive to structural choices such as joins, grouping, date handling, pivots, aliases, and CASE expressions. The pilot showed that lookup accuracy changes sharply with temperature, so this is the most informative Best-of-N axis. The goal is not to make lookup hotter globally, but to ask whether a selector can choose a correct SQL candidate when temperature explores multiple plausible query structures.

Analysis uses:

```text
bon_param=temperature
```

Reason: analysis output varies mainly in reasoning path, coverage, and wording. The pilot showed that `top_k_low` was a strong static setting for analysis, but Best-of-N should test the parameter where prompt-by-prompt candidate diversity is most meaningful. Static `top_k` tuning remains covered by Test 02.

Visualization uses:

```text
bon_param=top_k
```

Reason: visualization output is structured and parseability matters. The pilot showed `top_k_low` was a strong positive signal for visualization, while temperature-based Best-of-N at baseline was not useful. Varying `top_k` gives controlled diversity in chart/code choices without making the output unnecessarily unstable.

## CoT Choices

Run CoT only for:

```text
lookup_sales_data
create_visualization
```

Reason: these steps produce artifacts with concrete failure modes. SQL can be checked against execution/result shape, and visualization can be corrected for chart type, axes, grouping, invalid config, or code mismatch.

Do not run CoT for:

```text
analyzing_data
```

Reason: the pilot analysis CoT result was worse than baseline, and text scoring is less deterministic. Analysis already receives the extracted data and is less likely to benefit from a feedback loop than SQL or visualization.

## Thesis Objective

This test supports the discussion of whether a small thinking model should spend compute on extra candidates or feedback loops. It should separate three cases:

```text
useful extra compute      accuracy improves more than energy/time increases
neutral extra compute     accuracy stays within noise while cost rises
wasteful extra compute    accuracy drops or stays flat while cost rises
```

## Remote Docker Commands

Run from the repository root on the remote machine. Build the image once after pulling the branch:

```bash
docker build -t data-agent .
```

Start Ollama once outside Docker:

```bash
OLLAMA_HOST=0.0.0.0:11434 ollama serve
```

Pull the model:

```bash
ollama pull gemma4:e4b
```

Run two measured repeats sequentially on one GPU:

```bash
for REP in 01 02; do
  docker run --rm --gpus '"device=0"' --network=host \
    -e OLLAMA_HOST=http://localhost:11434 \
    -v "$(pwd)/runs:/app/runs" \
    data-agent \
    evaluation/run_manifest_benchmark.py \
    evaluation/benchmark_dataset_gemma4_thesis_10.json \
    evaluation/thesis_test04_gemma4_e4b_compute_expansion.yaml \
    --provider ollama \
    --model gemma4:e4b \
    --judge-provider ollama \
    --judge-model gemma4:e4b \
    --save-dir runs/thesis_tests/04_compute_expansion_n_and_cot/gemma4_e4b/rep${REP} \
    --resume
done
```
